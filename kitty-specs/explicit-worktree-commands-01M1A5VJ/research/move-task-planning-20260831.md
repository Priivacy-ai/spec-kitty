# Граница ремонта смены статуса

Дата: 2026-08-31. Аудитория: разработчик CLI. Проверенная база `3c9845044`.
Это подготовка дополнения к плану, не результат реализации или приёмки.

## Наблюдение

Реальный модульный вызов `agent tasks move-task WP01 --to doing --agent codex
--mission <slug> --json` при документах только во внешней рабочей копии вернул
`mission_not_found`, код 2. Проверка с запретом записей не изменила рабочие копии.
Другая команда с уже поддержанным `--owned-checkout` эти документы находит.
Новый регрессионный тест должен воспроизвести именно эту ошибку поиска,
а не только отсутствие нового флага в parser.

`resolve_owned_mission`, сохранение матрицы и существующий реальный Git-тест cwd.

Глобальную канонизацию путей, формат событий и reducer менять не требуется.

## База сравнения

Подтверждено: `resolve_owned_mission` требует current branch == target branch.
Если использовать target как review base, получится сравнение HEAD с HEAD.
Нельзя обходить проблему через `resolution_kind=repo_root`: существующая
`_validate_worktree_state` тогда пропускает проверки кода.

В проверенных модулях нет универсального строгого resolver базы: один путь
берёт `workspace.context.base_branch`, другой читает mission `planning_base_branch`,
затем оба могут вернуться к target. Для нового режима нужен отказ при отсутствии,
противоречии или непригодности существующей декларации; база фиксируется конкретной
ревизией/merge-base для diff и проверки implementation commit. Commit target
остаётся отдельным значением. Новые поля метаданных и исправление чужих документов
автоматически не вводятся.

## Критические проверки

Реальная цепочка `doing -> for_review -> in_review -> approved` и мотивированный
возврат из ревью; одинаковые имена работ с противоречащими статусами/базами;
ошибочные ownership/ветки/index/ссылки; непригодная review base; незавершённые
подзадачи и dirty code; отказ перехода после записи review и честная компенсация;
служебные annotations; старые вызовы без нового флага.

Тесты должны проверять содержимое событий, review bytes и Git snapshots, а не
только передачу kwargs или mocked writer. Для нового примера меняется один
ожидаемый статус; тест обязан упасть именно на неверном результате.

## Границы доказательства

Независимый разбор не запускал тесты и не менял файлы. Проверка профиля планирования
через изолированный resolver успешна. `charter context --no-mark-loaded` вернул
контекст корневой копии и пытался писать provenance/обращаться к сети; audit hook
отклонил эффекты. Это ограниченный запуск, не доказательство отсутствия эффектов
самой команды. Для этого плана полностью прочитан charter выбранной рабочей копии.

Необязательные режимы обхода guards не реализуются. Компенсацию обычного approval
исключать нельзя. Python-ограничения, Git hooks, общие служебные lock-файлы и custom
gate subprocesses не выдаются за полную OS-изоляцию. Никаких обещаний автоматического
прохождения приёмки другого проекта из этого анализа не следует.

## Независимое чтение плана

Ограниченный консультант прочитал только spec, plan, tasks, пакет работы и эту
заметку. Рекомендовал сохранить OwnedMission и отдельную базу сравнения; новый
resolver и фиктивный repo_root не обоснованы. До реализации потребовал уточнить
применимость базы, отделить формальную приёмку от подзадач и различить отказ ревью
от технического сбоя записи. Все три уточнения внесены основной сессией.

Основная сессия независимо сверила выбор базы и repo_root shortcut в production,
а `in_review -> planned` и освобождение agent/shell_pid - по существующим тестам
возврата. Выбранное дополнение T009-T013 последовательное; T005 теперь отражает
только доказанное техническое ревью прежней базы, не формальную приёмку.
Заключение консультанта является аудитом planning, не lifecycle-вердиктом.

## Проверка документов

Изолированный вызов полного `check-prerequisites --owned-checkout` остановлен
audit hook до `git remote show origin`: exit 1, одна запрещённая попытка remote,
без разрешённых записей. Полный `finalize-tasks` после этого не запускался.
Глобальные настройки, refs и защита не исправлялись ради зелёного отчёта.

Отдельно непосредственно выполнены штатные validators из `mission_finalize`:
occurrence-map, документы работ, извлечение требований, manifest, ссылки и граф
зависимостей, requirement mapping и conflicts. Итог: успешно, 1 пакет, 15 FR,
20 требований, 13 уникальных подзадач; предупреждений и запрещённых попыток нет.
Дополнительно сверены совпадение подзадач с frontmatter и незавершённость T009-T013.
Это проверка структуры, не полный CLI и не приёмка; защитный gate не обходился.

Новые человекочитаемые заголовки и проза проверены по-русски; технические имена
сохранены. Код, тесты и карта кода в этом пакете не менялись; новые тесты ещё
не запускались. Полная проверка приёмки остаётся открытой на ранее доказанной
границе. Hermes Kanban MCP в текущем наборе инструментов отсутствует.
