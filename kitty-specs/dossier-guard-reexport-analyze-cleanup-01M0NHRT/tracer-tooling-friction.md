## F-03 — `generate_tasks_md_from_manifest` has no mission-level preamble/notes field

**Verified first-hand**, 2026-08-22/23, during tasks authoring.

The tasking brief for this mission asked for the mission-wide baseline-capture command (and the
§106 change-scope-fold rationale for the #3678/SK-63 items) to appear "in `tasks.md`'s own
overview/preamble text — not buried in only one WP." Read the canonical generator directly
(`src/specify_cli/core/wps_manifest.py:170-218`, `generate_tasks_md_from_manifest`) before
assuming this was possible: it emits a fixed template —

```
# Work Packages: {feature_name}

_Generated by finalize-tasks from wps.yaml. Do not edit directly._

---

## Work Package {id}: {title}
**Dependencies** / **Requirement Refs** / **Plan Concerns** / **Owned Files** / **Subtasks** / **Prompt**
---
```

— with no field, hook, or notes/overview slot for mission-level prose of any kind. The function's
own docstring confirms this is deliberate: "Does NOT include implementation notes or risks —
those live in the WP prompt files." `finalize-tasks` overwrites `tasks.md` from this template on
every run (`mission_finalize.py:2754-2760`), so any hand-edit adding a preamble section would be
silently clobbered by a future `finalize-tasks` re-run with no warning — a worse outcome than not
adding it, since it would create a paper record that looks authoritative but isn't durable.

**Disposition**: per `CLAUDE.md`'s "Use Canonical Sources, Never Improvise" — trace and file the
gap rather than hand-roll a workaround that fights the tool. Not filing a new upstream issue in
this session (out of this authoring pass's scope; recorded here for the mission trail and for
whoever next touches `tasks-outline`/`tasks-packages`/`finalize-tasks` doctrine to decide whether
`WpsManifest` should gain an optional mission-level `notes`/`preamble` field). **Mitigation
applied instead**: the mission-wide baseline command, its disposition rule, and the §106 fold
rationale are stated in full in WP01's prompt file (the front-loaded, numerically-first WP, which
also owns subtask T001 = "capture the baseline"), and restated as an explicit
confirm-or-run-it-yourself instruction in WP02's, WP03's, and WP04's prompt files — so the
baseline requirement is unmissable across all four WP prompt files even though `tasks.md` itself
cannot carry it.

## F-07 — Round-3 fix: a truncated evidence quote in round 1 let a stale phrase survive two review rounds (process observation, not a tooling bug)

**Verified first-hand**, 2026-08-23, during the round-3 fix pass for
`reviews/tasks-round3.confirmed.yaml` (TASKS-FRESH2-001).

This is the third fix round in the tasks-phase review loop for this mission. The root cause
traces to round 1's fresh sweep (`reviews/tasks-fresh.yaml`, TASKS-FRESH-001): its own evidence
line for `spec.md:23`'s §106 change-scope sentence quoted only the sentence's closing clause
("now names a seventh file ... closes with 'No other file is touched, beyond the seven files
named above.'") as proof `spec.md` was "already fixed," and scoped remediation to `plan.md` only.
The same run-on sentence also contained an earlier, un-quoted clause — "...or fell outside this
six-file scope)" — that directly contradicted the quoted tail three words later. Because the
round-1 evidence excerpt never captured that earlier clause, round-1's reviewer, round-2's fixer
(commit `8e6888acc`, verified via `git diff 1543117f9 8e6888acc` to have touched only `plan.md`
and the four WP files), and round-2's own verify pass all treated `spec.md` as reconciled and
never re-read it. The residual phrase survived two full review rounds untouched, surfacing only
because round 3's fresh-sweep lens re-read `spec.md:23` in full rather than trusting the prior
round's evidence excerpt. Not a tooling defect — no ledger entry warranted — this is a process
observation for future review rounds in this same loop: an evidence quote that truncates a
sentence can hide a contradiction living in the un-quoted part of that same sentence, and a
"this file is already fixed" conclusion drawn from a partial quote is only as strong as the quote
is complete. Fixed here by rewording `spec.md:23`'s "fell outside this six-file scope" clause to
"fell outside the pre-fix file scope," which removes the ambiguity without needing a nested
parenthetical. A full `grep -n "six"` sweep of `spec.md`, `tasks.md`, and all four
`tasks/WP0{1,2,3,4}-*.md` files found no other file-count-scope contradiction (the only other
"six" hits, `spec.md:76` and `tasks/WP02-dossier-guard-widening.md:108`, both describe an
unrelated test fixture — "six bare positional arguments" — and are correct as written).
