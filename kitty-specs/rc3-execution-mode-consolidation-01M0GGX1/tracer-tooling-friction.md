# Tracer: tooling friction (M7 ExecutionMode consolidation)

Friction encountered driving this mission through the canonical `spec-kitty` surface.
Feeds the rc3 friction-burndown initiative directly.

## F1 — tasks_outline advance-guard requires `tasks.md`, but the outline prompt forbids writing it

- **Where:** `spec-kitty next` at `tasks_outline` → guard `Required artifact missing: tasks.md`
  (canonical manifest `packs/built-in/missions/software-dev/expected-artifacts.yaml`,
  `tasks_outline.path_pattern: tasks.md`), while the `tasks-outline` prompt says
  *"DO NOT write `tasks.md` — the system generates it from `wps.yaml`."*
- **Impact:** the loop cannot advance out of `tasks_outline` after writing only `wps.yaml`.
  `tasks.md` is actually generated by `finalize-tasks` (a *later* step), and `finalize`
  *parses dependencies from* `tasks.md` — a circular expectation.
- **Workaround used:** hand-authored a `tasks.md` in the template format to satisfy the
  guard; `finalize-tasks` then regenerated it canonically from `wps.yaml` (confirming the
  hand-written copy was throwaway scaffolding).
- **Suggested fix:** either (a) have `tasks_outline` generate `tasks.md` from `wps.yaml` at
  step exit, or (b) move the `tasks.md` requirement to the `tasks_packages`/`tasks_finalize`
  step so the guard matches the documented generation point.

## F2 — `_PUBLIC_SURFACE` in `test_mission_runtime_surface.py` is a vacuous pin

- **Where:** `tests/architectural/test_mission_runtime_surface.py:47` defines
  `_PUBLIC_SURFACE = sorted([...])` but no test asserts `mission_runtime.__all__ ==
  _PUBLIC_SURFACE`. The only surface test (`test_package_root_cold_imports`) merely checks
  the import succeeds.
- **Impact:** the spec treated this list as the governance "pin" for the retired
  `ExecutionMode`; in reality removing an entry produces no red. Symbol-surface drift on
  `mission_runtime.__all__` is currently unguarded.
- **Handled in-mission:** WP01 still removed the stale entry (keeps the list honest) and the
  ADR was updated; but the *real* red-first signal for the mission is WP02's new
  `test_execution_mode_no_redrift.py` guard.
- **Suggested follow-up (out of M7 scope):** make `_PUBLIC_SURFACE` load-bearing
  (`assert sorted(mission_runtime.__all__) == _PUBLIC_SURFACE`) or delete it as dead.

## F3 — planning `git grep` truncation under-scoped the WP ownership map

- **Where:** during planning, `git grep -n ExecutionMode -- tests/ | head -40` truncated the
  consumer list, so WP02's initial `owned_files` missed 4 rename targets
  (`tests/specify_cli/test_1716_closeout_regression.py`, `tests/tasks/*`).
- **Impact:** a strict ownership gate would have flagged out-of-map edits at review time.
- **Handled in-mission:** re-grepped without truncation in the lane worktree, widened
  `owned_files` (no overlap with WP01), and recorded it as a planning-consistency commit.
- **Lesson:** never `head`-truncate the grep that seeds a bulk-rename ownership map; count
  first (`git grep -l ... | wc -l`) then enumerate in full.

## F4 — `record-analysis` (and `implement`) fail-closed on a dirty tree, mid-loop

- **Where:** `spec-kitty agent mission record-analysis` → `DIRTY_WORKTREE`; `agent action
  implement WP02` → "Planning artifacts not committed" (auto-commit disabled).
- **Impact:** the loop repeatedly stalls until planning/status artifacts (`plan.md`,
  `research/`, `status.json`, dossier snapshot, `mission-events.jsonl`) are committed by hand.
- **Assessment:** the fail-closed behavior is *correct* (protects against mixing uncommitted
  state), but the friction is that the loop generates uncommitted status artifacts as a side
  effect of its own commands, so the operator must interleave `git commit` between steps.
  A single "commit planning/status artifacts" helper (or auto-commit-on by default for
  status-only churn) would smooth this.

## F5 — non-fatal but noisy: "project sync store is locked" on nearly every command

- **Where:** most `spec-kitty` invocations emitted `Warning: event journal capture failed:
  project sync store is locked` / `Event routing failed`.
- **Impact:** pure noise in this local/offline context (SaaS sync not engaged); had to be
  filtered from every command's output. Not a correctness issue for the mission.

## F6 — pre-review regression gate flagged "1 new failure" not reproducible in targeted runs

- **Where:** `move-task WP02 --to for_review` → "Pre-review regression gate: 1 new failure(s)
  across 7 affected shard(s)" (advisory — did not block).
- **Assessment:** not attributable to the change — a behavior-preserving *symbol* rename
  cannot break a test that does not reference the symbol name, and a whole-repo scan confirms
  no live old-name references remain (only cosmetic compound test-class names). 900+ targeted
  tests + the full arch suite are green. Classified as a flake/environment failure per the
  charter baseline-red gotcha (the gate runs in its own ephemeral built venv). The gate not
  surfacing the failing node id made attribution harder — persisting the failing test id
  would help.
