# Tracer: Approach

Seeded at planning per charter Standing Order #3 (mission tracer files).

## Reconcile-to-guard, never the reverse

All 8 named divergences between the three shipped manifests
(`research`/`documentation`/`software-dev`) and `runtime_bridge_cores.py`'s guard tables are
resolved by editing the **manifest** to match current **guard** behavior — never by editing
`runtime_bridge_cores.py`, `runtime_bridge_composition.py`, or `runtime_bridge_io.py`. This holds
even for divergence #8 (`software-dev/implement` requiring `analysis-report.md` that
`_evaluate_wp_iteration_guard` never checks), which reads at first glance like the guard is the
actual bug. It is not fixed here. Where a guard-side behavior looks wrong, the approach is to
file it as an independent follow-up issue and leave the runtime code untouched — consistent with
this mission's "content + schema only" scope and with not silently expanding blast radius into
consumer-behavior territory the issue itself never asked for.

## `plan`'s manifest is honest scaffolding, not a claim of enforcement

The new `plan/expected-artifacts.yaml` is authored against `plan` mission type's own
`mission.yaml` state machine and artifacts — not against `software-dev`'s CLI vocabulary, even
though that is the dispatch chain `plan`-type steps currently (and silently) fall through to. The
manifest says what `plan` missions actually produce; it does not claim `runtime_bridge_cores.py`
enforces it, because verified directly, nothing in that dispatch chain currently does. The
missing guard branch is filed as its own follow-up issue rather than patched in as part of this
mission — keeps the manifest fix and the runtime fix as two separately reviewable, separately
timed changes.

## Claim 6 is a carve-out, not a deferred TODO buried in code

The `artifact_key` vocabulary clash (manifest's dotted `"input.spec.main"` style vs.
`step.yaml`'s bare-identifier `template.artifact_key`) is named explicitly in the spec's
"Out of Scope" section with its own rationale (a contract change across two independently
versioned surfaces, per the charter's single-canonical-authority principle — needs its own scoped
mission with explicit versioning). It is not silently dropped and not fixed opportunistically
inside this mission's diff.

## Default: one PR per mission

This mission produces one PR against `main` covering the reconciled manifests, the new `plan`
manifest, the schema hardening, the `.kittify/overrides/` deprecation-header annotation (see
"A discovery that reframed part of the blast radius" below — **superseded by
`tracer-design-decisions.md` Decision 4**: header comment only, content otherwise untouched, not a
"drift-hygiene refresh"), and the test updates — not split across multiple PRs. The two follow-up
issues (plan-family guard gap; `artifact_key` vocabulary unification) are filed as tracker issues,
not as separate PRs, since neither is implemented as part of this mission.

## A discovery that reframed part of the blast radius

Mid-investigation, tracing `MissionTemplateRepository._expected_artifacts_path()` showed the
`.kittify/overrides/missions/*/expected-artifacts.yaml` copies are not consulted by any reader in
this repository for this specific file type (no override tier exists for it, unlike
`mission.yaml`/templates/command-templates, which do resolve through `.kittify/overrides/`
first). This changed the approach for that part of the blast radius from "reconcile two live,
consumed copies that could drift apart" to "fix the one consumed copy for correctness; mark the
dead mirror copy as deprecated/inert, since it currently misleads more than it helps." No new
override file is created for `plan` — creating a brand-new unconsumed file would add confusion
where none existed before, unlike annotating an already-present, already-dead one.

## Chokepoints & execution sequencing (tasks-authoring addendum, 2026-08-14)

Added while authoring `wps.yaml`/`tasks/WP*.md` (per this mission's tasks-authoring brief). This
is the durable home for this analysis — `tasks.md` itself is machine-generated from `wps.yaml` by
`finalize-tasks` ("Generated by finalize-tasks from wps.yaml. Do not edit directly.") and carries
no prose section, so it cannot host this write-up; each WP prompt's own Context section links back
here instead of to a nonexistent `tasks.md` section.

**No migration chain, runtime-state schema, event contract, or shared CI-gate file is touched by
this mission** (confirmed: zero overlap between this mission's file list and
`src/specify_cli/upgrade/migrations/`, `src/specify_cli/status/`,
`spec_kitty_events`/`spec_kitty_tracker` public surfaces, or `.github/workflows/ci-quality.yml`
itself) — so none of those chokepoint classes apply here. The one real chokepoint is narrower and
file-specific:

**`tests/dossier/test_manifest.py` is touched by four of the five WPs** (WP01 as sole
`owned_files` owner; WP02, WP03, WP04 each as a documented, small, well-justified
out-of-map edit adding one new, disjoint test class — `TestManifestReconciliation`,
`TestPlanManifest`, `TestOverrideMirrorDeprecation` respectively, alongside WP01's own
`TestSchemaHardeningAndLoudFailure`). Per current `lanes.json` (computed by `finalize-tasks` after
the structural fix described in "Revision history" below), the execution DAG is: `parallel_group
0` = {WP01} (sole owner, no declared dependencies); `parallel_group 1` = {WP02, WP03, WP04} (each
depends only on WP01, with no dependency edge among the three of them); `parallel_group 2` =
{WP05} (depends on WP01+WP02+WP03, and does not touch this file at all — its cross-cutting checks
land in a separate new file, `tests/dossier/test_manifest_guard_parity.py`, by design).

This means **four separate WPs — WP01 first, then WP02, WP03, and WP04 together in
`parallel_group 1` — can all touch the same file within the same execution window**, even though
their content edits are logically disjoint (distinct classes) — a real git-merge risk (independent
diffs each appending a new class near the end of the same file do not always three-way-merge
cleanly).

**Recommendation to the orchestrator** (sequencing advice, not a change to the WP dependency graph
declared in `plan.md`/`wps.yaml` — `plan.md` explicitly scoped IC-04 as "none — fully independent"
and IC-02/IC-03 as parallel-safe on content grounds, and this note does not silently override
either): the dependency graph permits WP02, WP03, and WP04 to run fully concurrently once WP01 has
landed — do not change that graph purely to serialize a file-level git-merge risk. But whoever
drives the implement-review loop should **land WP01 first and let it fully commit**, then
**sequence WP02, WP03, and WP04's own touches of `test_manifest.py` one at a time** (any order —
the three new test classes are mutually disjoint) rather than letting all three land concurrently,
for the same git three-way-merge reason given above. This is an execution-order recommendation for
whoever drives the implement-review loop, not a dependency the tasks/lanes machinery encodes
structurally — `owned_files` is file-granularity, not class/line-granularity, so the ownership
validator cannot itself distinguish "same file, disjoint class" from "same file, same lines."

**Concrete coordination protocol (added during analysis-findings remediation, to close the gap
between "advisory recommendation" and an actually-followable procedure):**

1. **Pre-flight check before starting any of WP02/WP03/WP04's `test_manifest.py` edit**: run `git
   log --oneline -3 -- tests/dossier/test_manifest.py` on the target branch. If a commit from
   another of {WP02, WP03, WP04} touching this file is not yet visible there, and that WP's own
   status (`spec-kitty agent tasks status`) shows it `in_progress`/`for_review` rather than
   `done`/`approved`, do not start your own edit concurrently — wait for it to land first, to keep
   the three-way merge trivial (pure append, no interleaving).
2. **If two of WP02/WP03/WP04 land concurrently anyway** (the dependency graph does not forbid
   it, so this can happen): the recovery is a standard git rebase, not a special procedure —
   `git fetch`/`git rebase <target-branch>` the later-landing WP's branch onto the
   already-merged one before opening its PR. Because the three new classes
   (`TestManifestReconciliation`, `TestPlanManifest`, `TestOverrideMirrorDeprecation`) are
   mutually disjoint blocks appended near the end of the same file, a conflict (if git's
   three-way merge cannot auto-resolve the block ordering) is resolved by keeping both classes,
   in either order — there is no semantic reason to prefer one class's position over the other.
3. **This protocol is deliberately kept out of `lanes.json`.** Encoding it there would require
   declaring `tests/dossier/test_manifest.py` in WP02/WP03/WP04's `owned_files` frontmatter, which
   would (a) require hand-editing WP frontmatter — forbidden by this mission's own operating
   rules and, more fundamentally, the wrong direction of fix, since `owned_files` frontmatter is
   the authored input `lanes.json` is *computed from*, not a file to reverse-engineer a desired
   `lanes.json` shape into — and (b) trigger the ownership-overlap conflict rule
   `src/specify_cli/lanes/compute.py` enforces between WPs with overlapping `owned_files` globs
   (verified by reading that module: overlapping `owned_files` are treated as a write-scope
   conflict signal, not a permitted shared-access declaration), which would either force WP01,
   WP02, WP03, and WP04 into a single merged lane or fail `finalize-tasks --validate-only`
   outright — undoing the whole point of the out-of-map-edit design (three independently
   reviewable, independently landable WPs). No CLI command was found that can add an advisory
   (non-ownership) file entry to a lane's `write_scope` without going through `owned_files`, so
   this is judged genuinely BLOCKED-for-hand-edit at the `lanes.json` layer, not merely
   unattempted — see `tracer-tooling-friction.md` for the corroborating note.

**Superseded by `tracer-design-decisions.md` Decision 4** (added during the adversarial-review fix
pass): the original framing above — "refresh the dead mirror copy for drift hygiene" — was
reconsidered and explicitly rejected. Refreshing the dead copies' *content* to match the
reconciled built-in manifests would be parity-with-a-dead-quirk, the exact DIRECTIVE_044
anti-pattern the "fix the one consumed copy" half of this decision already avoids. FR-014's actual
scope is a **header-comment-only** deprecation marker on each of the three dead mirror files —
content otherwise untouched, not refreshed. See Decision 4 for the full rationale and the two
rejected alternatives (refresh-to-parity; delete outright).

**Revision history** (how this section's DAG description and recommendation reached the current,
accurate state above — kept for audit trail, not because the text above still needs correcting):
this section originally placed WP04 in `parallel_group 0` alongside WP01 (true at authoring time,
since WP04 then had zero declared dependencies) and recommended a WP01-vs-WP04 ordering plus a
separate two-way WP02-vs-WP03 ordering. **TASKS-SEQ-001** (tasks-phase adversarial review, round 1)
flagged that framing as prose-only — an automated scheduler reading `lanes.json`'s
`parallel_group`/`depends_on_lanes` has no way to see prose, so WP01 and WP04 could be certified
safe to run concurrently by tooling even though this section said not to — and fixed it
structurally: `wps.yaml` now declares `WP04: dependencies: [WP01]`, and
`spec-kitty agent mission finalize-tasks` was re-run to recompute `lanes.json`/`tasks.md`, moving
WP04 out of `parallel_group 0` and into `parallel_group 1`. **TASKS-FRESH1-001** (round 2) then
caught that this structural fix had, as a side effect, produced an unnamed three-way
`parallel_group 1` collision (WP02/WP03/WP04, since all three depend only on WP01 and not on each
other) that no prose anywhere named yet, and added the three-way sequencing recommendation.
**TASKS-FRESH2-001** (round 3) found that the two rounds above had each appended a corrective
addendum *after* this section's original DAG-description sentence without ever fixing the sentence
itself, leaving three layers (a now-false original claim plus two addenda) instead of one coherent
account — this revision folds all three layers into the single corrected description above.
