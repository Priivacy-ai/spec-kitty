# Work Package Prompt: WP01 – Attribution guard hardening and predicate extraction

## ⚡ Do This First: Load Agent Profile

Run `/ad-hoc-profile-load python-pedro` (or the `spk-doctrine-profile-load` skill) and adopt its
identity, boundaries and governance scope before parsing the rest of this prompt.

## Objective

Make both attribution guards non-vacuous **per transport class**, and make each guard's predicate a
**callable module-level object** so the live corpus scan and the synthetic assertions exercise *the
same code*. This is the must-land-first package: US3 states this is the property that makes the
consolidation safe to attempt at all.

**Read first**, in this order: `../spec.md` → *Success Criteria* SC-005, SC-007, SC-012, SC-013 (and
their anti-vacuity notes, which are the whole content); `../plan.md` → **IC-01**, §Mutation suite
(MUT-4/5/6), §Verification Strategy rules 5, 10, 11, 15.

**Discharges**: **SC-005**, **SC-007**, **SC-012**, **SC-013**.
**Requirements**: FR-014, FR-015, FR-016, NFR-003, C-002.
**Blocks**: WP03. **Depends on**: nothing.

## The measured problem this WP exists to fix (PR-2 [HIGH])

Both attribution predicates are **local code inside a single test function body**, not importable
symbols — SaaS at `tests/specify_cli/saas_client/test_client_consent_gate_3030.py:~329-345` (inside
`test_every_production_construction_site_attributes_its_project`, which does `import ast`
in-function and inlines the `is_direct` / `is_from_env` / `attributed` logic), tracker at
`tests/sync/tracker/test_saas_client_consent_gate_3030.py:~383-390`, same shape.

Two binding rules collide with that:

- SC-012/SC-013 must be **asserted against a synthetic sample, not the live corpus** — but an inline
  predicate **cannot be called** on a synthetic sample; and
- **rule 11** mandates mutations be pytest plugins via `PYTHONPATH`, never source edits — but a
  plugin **cannot patch logic inside a function body**, and MUT-4/MUT-5/MUT-6 mutate exactly that
  logic.

**The failure if you take the path of least resistance, and it is silent.** Re-writing the predicate
in the new test makes a **second copy**. MUT-4/5/6 then mutate one copy while SC-012/SC-013 assert
against the other: the mutants become unkillable, or are applied to the copy and reported as kills
that prove nothing about the live guard. The plan already names that failure shape for SC-005 —
*"a harness that can drift from the real guard is a gate that goes green while the guard goes
blind"*.

> **BINDING SENTENCE — this is the point of the whole extraction.**
> *A synthetic assertion that does not call the same predicate object the live scan calls does not
> satisfy SC-012/SC-013.* **One object, two callers.** Two objects with the same source text is the
> state that goes green while the guard goes blind.

### T003 — Prove the hoist is behaviour-preserving, and prove it with something the counts can see

- **Counts, both sides.** Re-run the live scan before and after and quote
  `SaasClient scanned=4 unattributed=0` / `SaaSTrackerClient scanned=3 unattributed=0`, **with the
  input file count printed** (measured baseline: **937** files under `src/specify_cli`, rule 5). An
  extraction that moves a count is a rewrite, not a hoist.
- **The counts alone are not sufficient proof, and the plan measured why** (PR-E). MUT-4's counts are
  *exactly unchanged* (`scanned += 1` runs **before** the attribution test in both guards); MUT-5's
  `scanned == 3` sits *exactly at the floor*; MUT-6's `scanned == 4` is unchanged because the live
  corpus is `direct=0, from_env=4`. `unattributed=0` is equally blind — every live site is already
  attributed. **An extraction that accidentally widened or narrowed a predicate would emit
  byte-identical before/after evidence and pass the stated proof.**
- **So additionally record, for each of these four synthetic witness shapes, its `(matched,
  attributed)` tuple before and after the hoist, with the expected value derived by reading the
  pre-hoist source**:
  - `SaaSTrackerClient(repo_root=…)`
  - `SaasClient.from_env(project_root=r)`
  - `mod.SaaSTrackerClient(project_root=…)`
  - `SaasClient(project_root=…)`

  These four are **exactly the shapes the live corpus does not contain**, which is why they
  discriminate a widened or narrowed predicate and the live-scan counts do not.
- **Control first** (rule 10): the pre-hoist tuples are computed by transcribing the inline predicate
  into a scratch probe and checking it against the four shapes *before* you trust it.

### T005 — SC-012: per class, a form the guard **rejects** (synthetic, through the extracted predicate)

- **Tracker**: `SaaSTrackerClient(repo_root=…)` is **matched and flagged unattributed** — the tracker
  guard accepts `project_root=` only.
- **SaaS**: `SaasClient.from_env(project_root=r)` is **matched and FLAGGED unattributed**, because
  `from_env` accepts only a bare positional or `repo_root=`.
- **The SaaS witness is named explicitly because the obvious one is vacuous** (DB-4): *"the SaaS
  guard is not widened to admit tracker-only spellings"* is **vacuously true** — the tracker accepts
  exactly `{project_root=}`, which the SaaS guard **already** accepts for *direct construction*. That
  phrasing bites nothing. The `from_env` form is the one that flips the moment the SaaS vocabulary is
  widened.

### T006 — SC-013: per class, a **MATCH** on a shape no `src/` site uses

- **Tracker**: `mod.SaaSTrackerClient(project_root=…)` — an attribute-receiver call the
  `getattr(func, "attr", None)` predicate accepts. All three live tracker sites are bare `ast.Name`
  callees, so nothing in the corpus exercises it; unifying on the SaaS guard's stricter predicate
  would blind the guard to it **while leaving the count exactly at its floor**.
- **SaaS**: `SaasClient(project_root=…)` — bare direct construction. Measured corpus:
  **`direct=0, from_env=4`**, so this shape is *matched but unused*, exactly parallel to the
  tracker's. A unification collapsing onto the `from_env` form drops it **silently, with no count
  moving**.
- **NO NON-MATCH IS ASSERTED ANYWHERE.** Pinning `mod.SaasClient(...)` as must-not-match was proposed
  and **withdrawn on measurement in round 3**: the SaaS predicate is already the *stricter* of the
  two, so unification can only **loosen** it — the guard would see *more* constructions, a coverage
  **gain**. A non-match pin would red on an improvement and **collide with FU-8**, which exists
  precisely because `mod.SaasClient.from_env(x)` is unguarded on both guards and closing it means
  **widening** a predicate. `mod.SaasClient(...)` may stay in a diagnostic corpus; it may **not**
  become a test assertion.

### T007 — MUT-4 / MUT-5 / MUT-6 (mandatory evidence)

**Mechanism, binding**: each is a `pytest` plugin on `PYTHONPATH` that rebinds the **extracted
predicate symbol** by dotted path in `pytest_configure`. **No source edits during a verification run
(rule 11).** Write the plugins **outside the repository tree** (a scratch directory), never under
`kitty-specs/`, never committed.

**Rule 15, and it bites hardest here**: MUT-4/5/6 are the only plugins that reach a symbol in a
*test* module by dotted path whose target **does not exist until T001/T002 create it**. A rename
during the hoist, a wrong dotted path, or rootdir not on `sys.path` at `pytest_configure` each gives
a silently absent target, "mutant survived", and **a false finding about the code rather than about
the mutation**. Every plugin must **assert its target exists and fail loudly if it does not**.
