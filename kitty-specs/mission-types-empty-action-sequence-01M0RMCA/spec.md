# Mission Specification: Org/project-layer mission types resolve an empty action sequence

**Mission Branch**: `fix/mission-types-empty-action-sequence-3701`
**Created**: 2026-08-24
**Status**: Draft
**Input**: GitHub issue [`Priivacy-ai/spec-kitty#3701`](https://github.com/Priivacy-ai/spec-kitty/issues/3701) — "Org/project-layer mission types always resolve an empty action sequence: the step projection is hardcoded to `pack_context=None`"

## Summary

This is a **bug-fix / infrastructure-defect mission**, not a new user-facing feature. `_inject_projected_fields()` in `src/doctrine/missions/mission_type_repository.py` (currently lines 209–253) derives a mission type's `action_sequence` from its `mission-steps/<type>/<step>/step.yaml` files, but hardcodes `pack_context=None` at its call into `MissionStepRepository.default().resolve_all_for_mission_type(mission_type_id, pack_context=None)` (currently line 245). Every caller of this function — including the layered org/project mission-type loader (`_load_layered_mission_type_file`, currently line ~347, itself reached from `scan_mission_types_dir` → `resolve_layered_mission_types` and from `charter/pack_manager.py:865`) — therefore only ever sees the built-in `mission-steps/` tree. An org- or project-tier mission type that ships a complete `mission-steps/<type>/<step>/step.yaml` set (with `sequence_index`/`in_action_sequence` on each step) and no explicit `action_sequence:` in its own `<type>.yaml` resolves `action_sequence = None`, even though the sibling roster-lookup layering (fixed by #3397) correctly finds the type itself. Every governed entry point for that type then fails loudly with `MissionTypeEmptyActionSequenceError` (`src/charter/mission_type_profiles.py:1008`, added by #3386) — correct as a symptom report, but naming the wrong cause.

The "user" of this mission is a spec-kitty operator, an org/project mission-type pack author, or another mission's spec author who declares an org-tier mission type and expects it to behave like a built-in one.

## Clarifications

Two candidate decision forks were investigated ahead of this spec (by a prior researcher, "Robbie") and resolved with direct code evidence. Both are binding design inputs for this spec and for the plan/tasks that follow it — not background trivia. A later `sk-review` pass should audit both against the shipped diff.

### Decision 1 — thread `PackContext` into this seam, or migrate to consumption-boundary sourcing (as `template_set` already did)?

**RESOLVED: Thread `PackContext` into the seam. Do not migrate `action_sequence` to consumption-boundary sourcing.**

Evidence:
- `template_set` underwent a deliberate, **already-completed** full retirement from the `MissionType` model (mission `mission-step-creatability-01KXQA6R` WP01/FR-001): it is no longer read, written, or present on the model at all. `_inject_projected_fields`'s own docstring (`mission_type_repository.py:226-236`, this checkout) states this explicitly: *"the persisted field and its overlay are retired entirely — this function no longer reads or writes a `template_set` key at all... Consumers now source the template mapping from the step authority directly at the consumption boundary (`charter.mission_type_profiles._resolve_template_set_slot`), not from this repository-load-time injection."*
- `action_sequence` has had **no** such migration. It remains a first-class `MissionType.action_sequence: list[str] | None` model field (`src/doctrine/missions/models.py:261`), validated by `validate_action_sequence` at model-build time (`models.py:281-282`), and read via direct `.action_sequence` attribute access at ten real call sites (docstring/comment mentions of `.action_sequence` excluded) across `src/charter/mission_type_profiles.py` (×2, lines 985/994), `src/specify_cli/cli/commands/mission_type.py` (×2, lines 1469/1479), `src/runtime/next/decision.py` (×1, line 614), `src/runtime/next/runtime_bridge_composition.py` (×2, lines 188/325), `src/specify_cli/cli/commands/charter/mission_type.py` (×1, line 158), and `src/specify_cli/cli/commands/charter/activate.py` (×2, lines 183/205).
- `_inject_projected_fields`'s own docstring calls the `action_sequence` raw-YAML fallback (`payload["action_sequence"] = projected_sequence or raw.get("action_sequence")`) "C-007-retained, transitional" — i.e. explicitly still in force, not superseded.
- No ADR or docstring anywhere in the checkout signals an equivalent `action_sequence` migration is authorized.
- Threading the context mirrors the pattern `resolve_layered_mission_types` already uses successfully for the type roster itself (the #3397 fix), and mirrors `_resolve_template_set_slot`'s own already-working, already-production-consumed pattern of threading a real `PackContext` at the point that needs org/project data (SK-82, ledger).

Conclusion: this mission threads `pack_context` through the seam (`_inject_projected_fields`, `_load_layered_mission_type_file`, `scan_mission_types_dir`, `resolve_layered_mission_types`) rather than attempting a `template_set`-style retirement of `action_sequence` from the model.

### Decision 2 — does the activation-gate fix (a type with an empty sequence can still be activated) belong in this mission?

**RESOLVED: No. Out of scope for this mission.**

Evidence:
- Issue #3701's own Non-goals section names this explicitly: *"Not the activation-time validation gap (a type with a genuinely empty sequence can still be activated into a broken project) — that is #3702."*
- `#3702` is confirmed open and unassigned (checked as part of mission readiness).
- SPEC-KITTY-LEDGER.md entry **SK-81** (verified first-hand, mission `int-hybrid-install-01M0PY2E`, 2026-08-23) independently documents the *consequence*: `charter activate mission-type <T>` succeeds even when `<T>` resolves an empty action sequence, writing the activation and reporting success on run 1, with the failure only surfacing on the *next* invocation — after the project is already activated into a broken state.

Conclusion: SK-81 is cited here as **motivation** for why this mission's defect is dangerous (a project can be silently walked into an unusable activated state), but the activation-gate fix itself — making `charter activate mission-type` itself check and refuse — is issue #3702's work, not this mission's. This mission fixes the *projection*, not the *activation-time check*.

### Ledger context used to sharpen this spec's scope boundary (SK-82)

SPEC-KITTY-LEDGER.md entry **SK-82** (verified first-hand, mission `int-hybrid-install-01M0PY2E`, 2026-08-24) establishes that the `template_set` projection path *already* threads a real `PackContext` (via `charter.mission_type_profiles._resolve_template_set_slot`) and is consumed in production by `specify_cli/runtime/resolver.py` — and that a QA-pack doctrine document's "unwired, not absent" claim about org/project-layer `MissionStepRepository` resolution is **stale**: that org/project override path is reachable today, through that one route. This sharpens exactly which resolution paths thread a real `PackContext` today (`template_set`, via `_resolve_template_set_slot`) versus which do not (`action_sequence`, via `_inject_projected_fields` — this issue). This mission closes that one remaining gap; it does not re-open or re-verify the `template_set` path, which is already correct and explicitly out of scope (see Constraints, C-002).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - An org-tier mission type with steps-only projection resolves its action sequence (Priority: P1)

An org/project mission-type pack author ships a `mission_types/<type>.yaml` file with no explicit `action_sequence:` key, relying on the documented projection from that type's own `mission-steps/<type>/<step>/step.yaml` files (each carrying `sequence_index` and `in_action_sequence: true`), exactly as every built-in mission type already does. When this org type is resolved — via `resolve_layered_mission_types`, via `charter activate mission-type`, via `agent mission create --mission-type <type>`, or via any other governed entry point that reads `.action_sequence` — it resolves the correctly ordered, non-empty step id list, mirroring how a built-in type resolves its own `action_sequence` from its own step tree.

**Why this priority**: This is the only user story grounded in the issue. It is P1 because it is the entire defect: every org/project mission type that relies on step-file projection (the documented, intended way to define a type's action sequence without hand-authoring it) is completely unusable today — `MissionTypeEmptyActionSequenceError` fires on every governed read, per SK-81's reproduction. There is no smaller or larger honest slice of this issue; it is fixed as one unit or not at all.

**Independent Test**: Can be fully tested by constructing a synthetic org pack (a `mission_types/<id>.yaml` with no `action_sequence:` key, plus a `mission-steps/<id>/<step>/step.yaml` tree carrying `sequence_index`/`in_action_sequence`), pointing a real `PackContext` at it, and asserting `resolve_layered_mission_types(...)[id].action_sequence` is the expected non-empty, correctly ordered list — without touching any built-in type. Delivers value on its own: it is the complete fix, independently verifiable against the issue's own reproduction transcript.

**Acceptance Scenarios**:

1. **Given** an org pack with `mission_types/qa.yaml` (no `action_sequence:` key) and `mission-steps/qa/<step>/step.yaml` for seven steps each carrying `sequence_index` and `in_action_sequence: true`, and a `PackContext` built from a project that activates this org pack, **When** `resolve_layered_mission_types(mission_types_dirs, pack_context)` is called, **Then** the returned `MissionType` for `qa` has `action_sequence == ['discovery', 'specify', 'plan', 'tasks', 'implement', 'review', 'accept']` (the step order defined by `sequence_index`), not `None` and not `[]`.
2. **Given** the same fixture, **When** any other src/ call site that reaches this seam through `resolve_layered_mission_types` (e.g. `charter.mission_type_profiles._resolve_action_slot`, which underlies `charter activate mission-type qa` and `agent mission create --mission-type qa`) resolves the `qa` type, **Then** it succeeds and does not raise `MissionTypeEmptyActionSequenceError`.
3. **Given** the same fixture, **When** the four built-in mission types (`software-dev`, and the other three shipped in `packs/built-in/missions/mission_types/`) are resolved through the identical `resolve_layered_mission_types` call with a real, non-`None` `PackContext` present (one that declares an unrelated org pack, per the existing `TestGoldenParityUnaffectedByPackContextThreading` pattern in `tests/runtime/test_runtime_seam.py`), **Then** each built-in type's `action_sequence` is byte-identical to its value when resolved with `pack_context=None` — the fix must not perturb built-in resolution.
4. **Given** an org pack `mission_types/<id>.yaml` that DOES author an explicit `action_sequence:` list directly (the pre-existing, still-supported authoring path), **When** it is resolved, **Then** its explicit `action_sequence` is preserved unchanged (the projection fallback in `_inject_projected_fields` — `projected_sequence or raw.get("action_sequence")` — must continue to defer to a non-empty raw-authored value whenever the projection itself is empty).
5. **Given** a project-layer `.kittify/missions/mission_types/<id>.yaml` override with its own `mission-steps/<id>/` steps-only projection (no explicit `action_sequence:`), **When** resolved, **Then** it also produces the correct non-empty `action_sequence` — the fix applies uniformly to the org layer and the project layer, both of which are threaded through the same `pack_context`.

### Edge Cases

- **What happens when a mission type's own step tree genuinely projects to an empty sequence (no steps carry `sequence_index`/`in_action_sequence`) even with a real `pack_context` supplied?** The existing C-007-retained fallback (`projected_sequence or raw.get("action_sequence")`) applies unchanged: an empty projection falls back to the raw YAML-authored `action_sequence` value (which may itself be `None`). This mission does not change that fallback's behavior or `MissionType`'s non-empty-`action_sequence` model invariant — it only ensures the projection that feeds the fallback sees the correct, fully-layered step set instead of a built-in-only one. A genuinely and correctly empty result still surfaces via the existing `MissionTypeEmptyActionSequenceError` at the read boundary (unchanged, out of scope — see Constraints C-003 / Decision 2).
- **What happens to a mission that is mid-flight (already running, using a previously-resolved `action_sequence`) when this fix lands?** Benign. `_inject_projected_fields`, `_load_layered_mission_type_file`, `scan_mission_types_dir`, and `resolve_layered_mission_types` are pure projection/read functions, not state mutators — they do not touch `mission_type_activations`, event logs, or any other mission-state artifact. `resolve_layered_mission_types` is process-cached (`functools.cache`, keyed on `(mission_types_dirs, pack_context)`, per its own docstring's cache-safety-boundary section, this checkout), and each `spec-kitty` CLI invocation is a fresh process under the documented one-process-per-invocation model, so no live process holds a stale pre-fix result across the code change landing.
- **What happens when `MissionStepRepository.default().resolve_all_for_mission_type(...)` itself fails (malformed step YAML, unreadable directory) once fed a real `pack_context`?** Unchanged from today's built-in-only behavior at that boundary: `MissionStepRepository`'s own org/project resolution already loud-fails on malformed/unreadable input (out of scope — not this mission's code) rather than silently dropping steps. This mission does not add a new failure mode; it exposes the resolver's existing loud-fail behavior to org/project step trees for the first time, which is the intended and desired effect (silent success is this repo's dominant failure mode — this fix moves a defect class from "silently wrong" to "either correct or loudly wrong," never "silently wrong" for a different reason).
- **What happens when a caller other than `resolve_layered_mission_types` or `_load_layered_mission_type_file` invokes `_inject_projected_fields` directly without a `pack_context`?** `MissionTypeRepository._load()` (the `cls`-keyed, built-in-only cache, `mission_type_repository.py:165`) is the one remaining caller with no `pack_context` to thread — its existing zero-argument call requires no source change: `_inject_projected_fields`'s new `pack_context` parameter defaults to `None` (see FR-005/C-001), so `_load()` already behaves correctly through that default. This is correct, not a gap, and not a fifth touched function under C-007 — `_load()` only ever scans the built-in tree and its call site is untouched by this mission.
- **What happens at `charter/pack_manager.py:865`'s call into `scan_mission_types_dir`?** That call site only consumes the returned `MissionType.id` and the caller-supplied `layer` label for its `AvailableArtifact` catalog entries — it never reads `.action_sequence`. It keeps passing no pack context (or `None`, once `scan_mission_types_dir` gains the optional parameter) unchanged; this is safe because its consumption is limited to `.id`, not the field this mission fixes.

### Key Entities

- **`MissionType`** (`src/doctrine/missions/models.py`): the Pydantic model this mission's fix ultimately populates correctly. Carries `action_sequence: list[str] | None`, validated non-empty by `validate_action_sequence`. Not modified by this mission — only the data fed into its construction (via `_inject_projected_fields`'s `payload`) changes.
- **`PackContext`** (`src/charter/pack_context.py`): the structural object (`pack_roots`, `repo_root`, `activated_mission_types`, etc., built via `PackContext.from_config(repo_root)`) that already carries everything needed to resolve org/project layers. This mission's entire fix is "hand this object one layer deeper than it currently reaches."
- **`MissionStepRepository`** (`src/doctrine/missions/mission_step_repository.py`): already correctly resolves org/project step overrides when given a real `pack_context`; this mission changes none of its internals, only what argument `_inject_projected_fields` passes to `resolve_all_for_mission_type`.
- **The projection seam** (`_inject_projected_fields` → `_load_layered_mission_type_file` → `scan_mission_types_dir` → `resolve_layered_mission_types`): the four-function call chain this mission threads `pack_context` through, end to end.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An org-tier mission type with a complete `mission-steps/<type>/<step>/step.yaml` tree (each step carrying `sequence_index`/`in_action_sequence`) and no explicit `action_sequence:` in its own `<type>.yaml` resolves the same non-empty, correctly-ordered `action_sequence` whether reached via `resolve_layered_mission_types` or any layered call site reachable from it (`charter.mission_type_profiles._resolve_action_slot`, `charter activate mission-type`, `agent mission create --mission-type`), matching exactly what a real `PackContext` already produces for `MissionStepRepository.resolve_all_for_mission_type` directly — reproducing the issue's own repro transcript (`qa -> ['discovery', 'specify', 'plan', 'tasks', 'implement', 'review', 'accept']` instead of `qa -> None`).
- **SC-002**: `MissionTypeEmptyActionSequenceError` no longer fires for any org/project mission type whose only defect was an unprojected (rather than genuinely empty) step tree — i.e. the error's remaining trigger set is exactly "a type whose step tree, once correctly layered, still projects empty and has no raw-authored fallback," never "a type whose step tree was simply never looked at."
- **SC-003**: All four built-in mission types resolve byte-identical `action_sequence` values before and after this fix, under both `pack_context=None` and a real non-`None` `pack_context` — zero built-in behavior change (measured by `tests/runtime/test_runtime_seam.py`'s golden-parity suite passing unmodified in its assertions, only extended in setup if needed).
- **SC-004**: The new red-first test (NFR-001) fails against the pre-fix code (reproducing `None`/`[]`) and passes against the post-fix code — verified by running it against a git stash/revert of the fix during review, not merely asserted. **Owning actor and moment**: the WP-implementer authoring NFR-001's test must, before marking the WP done, `git stash` the mission's changes to `mission_type_repository.py`, rerun the new test and confirm it fails with the pre-fix `None`/`[]` result, `git stash pop`, and rerun to confirm it then passes — and must record both runs (command + observed result) in the mission's `tracer-approach.md` or `tracer-design-decisions.md` so the pre-merge (sk-review) squad can verify the claim was witnessed rather than re-deriving it.
- **SC-005**: `pytest tests/doctrine/missions/test_mission_type_repository.py tests/runtime/test_runtime_seam.py` passes in full post-fix, with no newly-introduced red beyond the pre-existing ~23 known-red-test / 2-error baseline already on `main` (issue #3284, SPEC-KITTY-LEDGER.md) — any red in this run must be individually triaged as pre-existing or mission-introduced, never waved through as "the suite is red." **Triage mechanism**: run the identical pytest invocation against the mission's unmodified base commit; a given red test that is also red there on the same test id is pre-existing (log it against a tracked issue rather than #3284's own breakdown, which does not enumerate either of these two test files); a test that is green on the base commit and red post-fix is mission-introduced and must be fixed before merge.

Any other path appearing in the diff is a C-002/C-003/C-007 violation and must be justified or removed before merge.
