## 1. ADR amendment — the #1667 / C-004 chain (Q4 rider, directive 003)

**Amendment to the "MissionStatus is the authoritative write entry point" chain (#1667, C-004).** The word *authoritative* carries two senses in the status write path, and they now name two different things — deliberately, so the term does not become another `primary`/`merge`-style footgun:

1. **Domain facade (intended, unchanged intent).** `MissionStatus` (`status/aggregate.py`) remains the intended domain facade for callers of the status write path: it owns the read-surface resolution (coord-aware, fail-closed on a deleted coord worktree), the mission identity, and the guard input it alone can see (`current_actor`). It is *not* the write chokepoint today: eight production callers still invoke `emit_status_transition_transactional` directly (`merge/done_bookkeeping.py:268,:421`, `orchestrator_api/commands.py:1742`, `lanes/recovery.py:803`, `status/bootstrap.py:166`, `status/work_package_lifecycle.py:230,:295`, `cli/commands/implement.py:1459`; `research.md` §1.1), and two batch callers invoke the batch door. Their migration is a **future caller-migration mission**, not this one — routing them through the aggregate today would bless the aggregate's lazy `coordination` import (the C-006 precedent violation) as the front door, and would change flat/`LANES` semantics by another door (C-008). That lazy import (`status/aggregate.py`, inside `MissionStatus.transition`) is kept and commented as the one existing exception; no second reach was added.
2. **Validation/build authority (new, this mission).** `status/transition_pipeline.py::prepare_transition` is the single place in the tree where a status transition is validated and its `StatusEvent` is built. Every write door composes it: the flat/primary shell (`status/emit.py`, single + batch), the transactional shell (`coordination/status_transition.py`, single + batch), and — through the transactional shell — the aggregate. `validate_transition` is called exactly once per emit, tree-wide (US2-4; pinned by `tests/status/test_agent_status_emit_aggregate_wiring.py::test_validate_transition_runs_exactly_once_through_the_aggregate` and `tests/specify_cli/coordination/test_status_transition.py::test_three_doors_build_the_same_event_and_validate_once_each`).

Consequence, restated from `research.md` §1.2 option 2: "one orchestrator" means **one pure pipeline + exactly two shell kinds** with explicit per-shell failure policies (C-007). Lock acquisition, commit ordering and fan-out timing are shell responsibilities by design; the phantom fan-out fix (FR-008) was therefore a shell fix, made in the coord fallback arms of the transactional shell. WP03's shell-proliferation gate polices a third composition of lock + append.

## 4. FR-008 — how the phantom was closed

`_emit_on_coord_then_commit` is the one coord fallback arm both doors share: flat shell with `fan_out=False` → `safe_commit` → `_fan_out_committed_coord_tail`. The deferred step 7 reads only the bytes appended past the pre-emit snapshot (`_snapshot_coord_status_artifacts` already recorded the size) and parses them with `store.read_event_stream_from_text` — so it announces exactly the rows the commit made durable: lane events via `_saas_fan_out` and resolved-binding annotations via `_resolved_binding_fan_out`. This is why the annotation survives the deferral although the flat shell returns only the `StatusEvent`: the annotation is recovered from the committed tail, never re-minted. `policy_metadata` is read off the persisted event (the pipeline stamps `request.policy_metadata` onto it — the same value the flat shell passed). The batch arm fans out with `requests[0].repo_root` (one lifecycle operation, one emitting checkout; per-member `repo_root` never differs in production and the batch identity check already anchors on the first member). On the failure path the `finally` only restores; the fan-out call is after the `try`, so it is unreachable when the commit raised (SC-002 pinned single + batch). RED proof on the base: `order == ['fan_out', 'commit']` (single) and `['fan_out', 'fan_out', 'commit']` (batch).

| **D-1** (`effective_root` → `resolve_subtasks_gate_dir`; flat shells drop it via `_flat_subtasks_dir_resolver`, the pipeline default threads it) | **Keep WP02's adapter; no change to `status/emit.py`.** The transactional doors compose the pipeline with its default resolver, so they thread `request.effective_root` exactly as `_prepare_event` did (behaviour preserved). ## 7. Plain-door pin (C-008 / SC-007) — what "no identity-resolution git subprocess" means at HEAD

The contract §5 wording was refined by measurement. With `subprocess.Popen` recorded, the plain door on a primary path spawns exactly one git process on the write path: `git rev-parse --git-common-dir` from `status/locking.py::feature_status_lock_path` (lock-file placement under the git common dir — WP01's territory, not identity resolution). The other spawns observed (`git config --get remote.origin.url`, `git remote get-url origin`) come from the zeitgeist bridge's origin lookup inside the outbound fan-out, i.e. the outbound side, not the write path. The pin therefore asserts: through `emit_status_transition_transactional` on a stored-`LANES` bare-slug mission — `_resolve_fallback_coord_worktree` returned `None` (the `_primary` arm), HEAD count unchanged, the write is uncommitted in the working tree, no `.worktrees/`, no mutating git verb (commit / worktree add / branch create / checkout / reset / merge / rebase); and through the plain door itself with fan-out patched — the recorded git argv is exactly `[rev-parse --git-common-dir]`. Rationale cites `_fallback_emit_single._primary`, not the four docstring mentions (research §3 D-1).
