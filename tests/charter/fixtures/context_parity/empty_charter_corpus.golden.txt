Profile-Cited Directives (generic-agent):
  - DIRECTIVE_028: Efficient Local Tooling — All agents must use low-noise, efficient tooling for repository operations as a baseline governance requirement.
    Intent: Local work should prefer efficient, low-noise tooling so investigation, editing, validation, and repository operations stay fast and reproducible across development environments.
    Scope: Applies to local repository investigation, file inspection, archive handling, copy or sync workflows, and command-line ergonomics used by contributors and agents during implementation and review work.
    Procedures:
      - Prefer fast, purpose-built local tools over slower or noisier generic shell patterns when an equivalent local capability exists.
      - Record local tooling availability, session decisions, and remediation notes in `.kittify/memory/available_tooling.md`.
      - Use operation-appropriate tools such as ripgrep for repository search, pagers for large-file inspection, and stream-oriented archive tools for compressed content.
      - Favor environment defaults and workflow choices that reduce local overhead, including repository-safe git settings and performant Windows or WSL workflows where relevant.
      - Favor tooling that filters output to only the information the agent needs, reducing token consumption on common dev operations, over commands that emit unfiltered noise.
      - Fall back to less efficient tooling only when the preferred local option is unavailable or does not support the required operation safely.
      - When a more efficient local tool is missing, warn the user that it exists and offer to guide them through installation or setup.
    Integrity rules:
      - Local guidance should bias toward faster, lower-noise tooling that keeps repository operations inspectable and proportional.
      - Tooling preferences and missing-tool decisions should be visible in the session tooling record instead of remaining implicit.
      - Default examples should avoid avoidable decompression, broad recursive scans, or platform choices that materially slow routine work.
    Validation criteria:
      - Agent and developer guidance recommends efficient local tools for the common repository operations it documents.
      - `.kittify/memory/available_tooling.md` captures the chosen local tools, missing-tool decisions, and any remediation guidance for the session.
      - New workflow notes avoid introducing slower generic shell patterns when a documented local tool provides the same behavior more directly.

Profile-Resolved Procedures (generic-agent):
  - adversarial-squad-deployment
    Name: Adversarial Squad Deployment
    Purpose: Deploy a small, bounded set of profile-loaded subagents in parallel at high-leverage review point-cuts so independent doctrine lenses converge on findings no single reviewer would catch. Turns review from one perspective into a cheap adversarial panel that resists laziness, accidental-pass, and single-lens blind spots. Optional and charter- or memory-activated — it enriches the flow, it does not gate it.
    Steps:
      - Choose the point-cut and the question
      - Select profiles by lens (bounded)
      - Dispatch in parallel, profile-LOADED
      - Require structured, non-fakeable output
      - Match model tier to task difficulty
      - Synthesize, and get a second opinion on divergence
      - Record the convergent evidence and act
  - bdd-scenario-lifecycle
    Name: BDD Scenario Lifecycle
    Purpose: Guide the Formulation, Automation, and Maintenance phases of the BDD cycle, picking up where the Example Mapping Workshop (Discovery phase) leaves off. Covers translating validated examples into Gherkin specifications, wiring them to executable step definitions, and maintaining them as living documentation as the system evolves. Toolchain-agnostic — applicable with Cucumber-JVM, Cucumber-JS, Behave, SpecFlow, or any Given/When/Then runner.
    Steps:
      - Express each example as a Gherkin scenario
      - Validate Gherkin readability with a non-technical reviewer
      - Wire step definitions to application code
      - Run scenarios red, then implement until green
      - Publish to living documentation
      - Maintain scenarios as behavior changes
  - event-storming-discovery
    Name: Event Storming Discovery
    Purpose: Discover domain events, commands, aggregates, policies, read models, and bounded context boundaries through a structured analysis of business flows. The procedure produces a shared domain model grounded in real business behaviour rather than technical assumptions. Based on Alberto Brandolini's Event Storming technique, adapted for agent-assisted discovery with human-in-charge validation at key decision points.
    Steps:
      - Gather domain source material
      - Discover domain events (chaotic exploration)
      - Validate event completeness with domain expert
      - Identify commands and actors
      - Cluster into aggregates
      - Discover policies and read models
      - Propose bounded context boundaries
      - Review and confirm boundaries
      - Capture structured output
  - example-mapping-workshop
    Name: Example Mapping Workshop
    Purpose: Turn a behavior request into concrete rules, examples, and open questions that stakeholders and implementers can share as a canonical specification set.
    Steps:
      - Frame the behavior slice
      - Collect concrete examples and counterexamples
      - Separate rules, examples, and questions
      - Choose canonical examples
      - Confirm the source-of-truth set
      - Publish traceable outputs
  - legacy-codebase-triage
    Name: Legacy Codebase Triage
    Purpose: Convert an unfamiliar brownfield codebase into a defensible action plan by gathering version-control evidence, overlaying structural and complexity signals, optionally classifying domains, and bucketing the resulting findings into fix-this-week, fix-this-quarter, do-not-worry, and parallelisable work. The output is a triage document that anchors subsequent planning conversations and ADRs; it is not a replacement for deeper investigation, only a fast, evidence-backed first pass.
    Steps:
      - Confirm scope and exclusion list
      - Run the forensic repository audit
      - Cross-reference hotspots with bug and complexity data
      - Optional — apply strategic domain classification overlay
      - Optional — gather security and dependency signals
      - Bucket findings using Eisenhower prioritisation
      - Compile the triage report and review with stakeholders
  - mission-tracer-files
    Name: Mission Tracer Files
    Purpose: Give every mission a lightweight running log of tooling friction, approach evolution, and design rationale through three sparse tracer files. The files are seeded at mission start, appended to during implementation, and assessed at mission close. Captured friction and rationale feed the next mission's planning and make recurring tool and process gaps visible instead of repeatedly re-discovered.
    Steps:
      - Seed — create the three tracer files at mission start
      - Append — add dated entries during implementation
      - Assess — review and act at mission close
  - post-merge-arch-gate-adjudication
    Name: Post-Merge Arch-Gate Adjudication
    Purpose: After merging one or more lane branches, architectural gate failures may appear that were not visible during per-lane review. This procedure distinguishes pre-existing failures (present on the mission base branch before any lane work) from regressions introduced by the merge. Correct adjudication prevents teams from either ignoring real regressions or blocking on failures they did not cause.
    Steps:
      - Run the full architectural gate suite on the merged branch
      - Establish the pre-existing baseline via cross-base diff
      - Run CI-only shards locally before concluding
      - Adjudicate and record
  - red-main-release-discipline
    Name: Red Main & Release Discipline
    Purpose: Keep the mainline CI signal honest and authoritative for release. A red main is a true signal of known release-blocking (P0) defects, never something to hide by reverting an honest failure or declining a bug's reproduction test. Mainline CI status is the single authoritative release gate; expensive QA and manual testing are not spent on a known-broken base; and red main is worked down as top priority. Consensus policy (CEO/product owner, QA lead, maintainers); governing decision ADR 2026-07-17-1, operational guide docs/development/red-main-and-release-readiness.md.
    Steps:
      - Read a red main as honest signal, not a violation
      - On filing or accepting a P0, add a failing reproduction test
      - Gate release on green mainline CI
      - Defer expensive QA and manual testing until green
      - Prioritize red recovery
  - situational-assessment
    Name: Situational Assessment
    Purpose: Establish a shared, documented understanding of the context, stakeholders, constraints, and problem structure before any solution is designed or selected. A situational assessment ensures that architectural decisions are grounded in operational reality rather than technology preference, and that the trade-off assessments that follow address the right problem.
    Steps:
      - Draft the System Context Canvas
      - Validate the canvas with stakeholders
      - Decompose the problem
      - Identify and run pre-design experiments
      - Draft the Lightweight Prestudy
      - Review and accept the prestudy
